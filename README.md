**Shared oxlint, oxfmt and Knip presets for AntelopeJS projects, with a command that installs them and fails CI when they drift.**

[Documentation](./docs) · [All interfaces and providers](https://github.com/AntelopeJS/antelopejs#ecosystem)

</div>

The AntelopeJS guardrail pack: shared lint, format and dead-code presets, the commands that install and enforce them in a repository, and a check for the version ranges of interface dependencies.

- [oxlint](https://oxc.rs) and [oxfmt](https://oxc.rs) replace Biome: lint, format and Tailwind class sorting, `.vue` included.
- ESLint stays for the Nuxt front ends, from a shared config: oxlint runs no Vue template rule and no type-aware rule on `.vue` files.
- [Knip](https://knip.dev) learns the entry points of an AntelopeJS module.
- Every preset is a function: options adjust it without copying it.
- `antelopejs-sync` writes the configs, hooks, scripts and agent instructions into a repository, and `antelopejs-sync --check` fails CI when they drift.
- Every lint rule is an error or off.

## antelopejs-garden

`antelopejs-garden` is the Gardener's deterministic scan. It reads the AntelopeJS repositories through the GitHub API and the npm registry, authenticated with the token `gh` is logged in with. It never clones. Most checks read only the scope: the non-archived repositories whose `pack` property is `full` or `template` and whose `tier` is N1 to N3. The checks that read every non-archived repository, except `dms-cicd` and `cms*`, regardless of `pack` and `tier` say so below, such as `branch-governance` and `repo-admins`.

- `--json` prints `{ generatedAt, findings, prunes, skipped }`. A finding is `{ key, repo, check, subject, severity, evidence, doneMeans }` with the key `repo|check|subject`, sorted. `skipped` lists every check whose source does not exist yet, or that could not run.
- Without `--json` it prints failures only. The exit code is non-zero only when a check could not run.
- The `branch-governance` check reads the rules in force on the default branch of every non-archived repository except `dms-cicd` and `cms*`, whatever its `pack` and `tier`. It reports an `urgent` finding for each missing `deletion`, `non_fast_forward`, `required_linear_history` and `pull_request` rule (subject `<branch>:rule:<type>`), except that `k8s-gitops-infra`, whose own ruleset governs it, is not asked for `required_linear_history`. It reports a `normal` finding when no rule requires `verdict` or `ci / checks` from GitHub Actions (`<branch>:checks`), for repositories whose `pack` is `full` or `template` only. It also reports a `normal` finding when the branch has no `merge_queue` rule (subject `<branch>:rule:merge_queue`), except on `cloud`, whose merge queue is on `develop`, and on `k8s-gitops-infra`, `antelope-compliance`, `antelope-hardening` and `antelope-web`, which have no merge queue. It reads each ruleset that contributes a rule through the repository rulesets endpoint, which serves organization rulesets without the `admin:org` scope, and reports an `urgent` `<branch>:bypass` finding when its bypass list holds an actor other than the admin repository role in `pull_request` mode or the `antelopejs-release` GitHub App in `always` mode. A repository ruleset that still lets the Maintain role bypass is reported this way. One exception: the own ruleset of `k8s-gitops-infra` may also hold the admin repository role in `always` mode, because argocd-image-updater and the platform automation push straight to `main` through it; any other actor on that ruleset is still reported.
- The `repo-admins` check reads the collaborators of every non-archived repository except `dms-cicd` and `cms*` (`affiliation=all`, so direct, team and organization-owner access) and reports one `normal` finding per login that holds the `admin` role outside `Upd4ting`, `mwesto`, `dada-sudo`, `Thomasims` and `alessaloisio`. The finding has `repo` set to the organization, the subject `repo-admin:<login>` and the repositories in its evidence, so a person is one finding however many repositories they administer. The Maintain role is not read: it has no bypass on a default branch ruleset. The separate `governance-drift` check reports each organization owner outside `Upd4ting`, `mwesto` and `dada-sudo` (subject `org-admin:<login>`).
- The `org-checks-ruleset` check reads the organization rulesets and reports an `urgent` finding, with `repo` set to the organization, when `Default branch protection` or `Required CI` is missing or has drifted. `Default branch protection` must be active, target branches, match `~DEFAULT_BRANCH` and apply to `~ALL` repositories. `Required CI` must be active, target branches, match `~DEFAULT_BRANCH`, apply to the `pack` property values `full` and `template`, and require `verdict` or `ci / checks` from GitHub Actions. Both checks are accepted until the ruleset moves from `ci / checks` to `verdict`.
- The `flaky-tests` check lists the completed `merge_group` runs of `ci.yml` created in the last 14 days, once per repository, and reads the check suite of each. It reads the annotations only of check runs that report some, and keeps the `warning` annotations titled `Flaky test` that ci-node.yml v2 writes in the merge queue for a test that passed only on its retry. It reports one `normal` finding per repository and test (subject `<file> > <title>`, `<file>` or `pnpm run test`, the annotation message without its `<owner>/<repo>: ` prefix and ` passed only on its merge-queue retry.` suffix), with the number of distinct runs and the URLs of the 10 newest in its evidence, so a test flaky in several runs, or twice in one, is one finding. It reads every attempt of a run. Above 10 flaky tests in one step ci-node.yml names files instead of tests, and above 10 files `pnpm run test`, so one test can appear under a coarser subject in such a run. It is done when the test passes without a retry in the merge queue for 14 days. This is how a flaky test reaches the Gardener's Notion tasks: CI writes nothing to Notion.
- `--apply` turns `delete_branch_on_merge` on for each repository the `conformance` check reports it off on, and writes nothing else.
- The `stale-branches` check lists, in one finding per repository, the branches other than the default, `next`, `develop`, protected and `assets/*` ones that head a merged or closed pull request at their current commit, or have no open pull request and no commit for 30 days. A branch that heads or receives an open pull request is never listed. `prunes` holds one `{ repo, branch, reason }` per listed branch, and `--apply-prunes` deletes exactly those refs.

Both profiles of `antelopejs-sync` keep the shared CI caller on the job id `ci`, so the check is reported as `ci / checks`. The `ci` job is read-only (`contents: read`) and passes `renovate-sync: false` and `test-job: true`, an input ci-node.yml v2 accepts and ignores, since `single-job` alone picks the jobs (sync adds `test-job: true` to a caller that does not set it and keeps a value the caller set); it passes no secret, since ci-node.yml v2 ignores `NOTION_TOKEN` (sync removes a `NOTION_TOKEN` the caller passes, drops a `secrets` map that leaves empty and keeps `secrets: inherit`), and dms, antelopejs, dms-frontend, mongodb and dms-assistant, whose tests take minutes, also pass `single-job: false` so checks and tests run in parallel jobs; a single package, and a workspace whose root `test` script reaches every package `test` script through `pnpm -r`, `--dir` or `--filter`, also pass `affected-tests: true`, so a pull request runs only the affected tests (sync keeps the input when a repository sets it and never writes it for a workspace whose tests sit at the root or whose packages test more than the root runs, such as dms, dms-saas, dms-mailing, agent-skills and antelope-web); the `contents: write`, `actions: write` and `statuses: write` grants that let the Renovate sync push its commit, dispatch the caller and set the `ci / checks` status live on a separate `renovate-sync` job calling `ci-renovate-sync.yml`, which sync adds when it is missing and never re-pins. That job forwards the `RELEASE_APP_ID` and `RELEASE_APP_PRIVATE_KEY` secrets, which sync adds beside any secret of its own and skips under `secrets: inherit`, so the sync pushes with the release app's token and the push starts the pull request's checks. Under the full profile it also sets the `docs-files` input of every ci-node caller to the existing `README.md` and `docs` of the root and of each workspace package that is not private, then keeps the caller's other listed paths that still exist. Renaming a caller to `ci` also rewrites `needs:` lists and `needs.<old-id>` reads in expressions, and sync (and `--check`) fails a caller in which a job needs a job that does not exist or reads `needs.<id>` of a job missing from its own `needs:`, since GitHub evaluates that read to null and a gate like `needs.checks.result == 'skipped'` then never fails.

## antelopejs-triage

`antelopejs-triage` lists the issues Community Triage has not looked at yet, ranked, through one GitHub GraphQL search authenticated with the token `gh` is logged in with. An issue is listed when it is open, labelled `needs-triage`, has no assignee, sits in a public, non-archived AntelopeJS repository, and no open pull request is linked to it. A linked pull request that was closed does not hide the issue.

- The ranking puts bugs first, then features, then the rest, then the most 👍 reactions first, then the oldest first. The `bug` label sets the kind `bug`, the `feature` or `enhancement` label sets `feature`, and the issue type does when none of them is there.
- `--json` prints `{ items, notShown }`. `items` holds at most 10 `{ ref, url, kind, title, firstLine, created }`, with `ref` as `AntelopeJS/<repo>#<number>`, `kind` as `bug`, `feature` or `other`, and `created` as the `YYYY-MM-DD` date. `firstLine` is the first line of the body that is not blank, a Markdown heading, an HTML comment or `_No response_`, cut at 200 characters. `notShown` counts the listed issues past the tenth.
- Without `--json` it prints one line per item and a last line with the count not shown, and nothing when no issue waits.

## Writing skills

`antelopejs-sync` also installs the `technical-writing` and `unslop` skills in every full-profile repository and in a template source. Each is `.agents/skills/<name>/SKILL.md` with a `.claude/skills/<name>` link. The text is vendored from Upd4ting/agent-config `claude/skills/<name>/SKILL.md` at commit 4e0a848, minus the `technical-writing` paragraph that links the unsynced `docs/harness/claude-code.md`, and `--check` reports an edited file as drift. Write documentation with them: `technical-writing` picks the page's mode and sets the sentence rules, and `unslop` lists the patterns to cut.

## Verification skill

`antelopejs-sync` installs the `verify-changes` skill in every full-profile repository that has no `verify-*` skill of its own in `.agents/skills` or `.claude/skills`, the same way as the writing skills. It tells an agent which check to run for each kind of change, how to scope a test run to one file with at most 4 workers, how to start the services a test needs, and what CI and the merge queue run instead. It reads the commands from the repository's `package.json` scripts and its `## Tests` section, and copies none of them. The Guardrails block of `AGENTS.md` points to it.

A repository whose checks differ, such as a DMS or a template, writes its own `verify-<repo>` skill. Sync then installs no `verify-changes`, removes a copy it installed before, and points the Guardrails block to the repository's skill.

## Install

Node.js 24, or at least 22.18: oxlint reads `oxlint.config.ts` and loads JS plugins by executing TypeScript.

```bash
pnpm add -D @antelopejs/tooling-configs oxlint@1.95.0 oxfmt
```

The tools are optional peer dependencies, so add only the ones a repository uses:

| Tool                    | Packages to add                                                                  |
| ----------------------- | -------------------------------------------------------------------------------- |
| oxlint                  | `oxlint@1.95.0`, plus `oxlint-tsgolint` for the type-aware rules (on by default) |
| oxfmt                   | `oxfmt@^0.80.0`                                                                  |
| ESLint                  | `@nuxt/eslint-config`                                                            |
| Knip                    | `knip@>=6`                                                                       |
| Import sorting (opt-in) | `eslint-plugin-perfectionist`                                                    |

Pin `oxlint` to an exact version its peer range lists (**1.95.0**, 1.94.0 or 1.81.0): the JS plugin API is still alpha, so each listed version is checked against the `@oxlint/plugins` this package depends on.

## oxlint

```ts
// oxlint.config.ts
import { defineConfig } from "oxlint";
import { antelopePreset } from "@antelopejs/tooling-configs/oxc/lint";

export default defineConfig({
  extends: [antelopePreset()],
  // oxlint reads this field only from the root config, never from a preset.
  options: { typeAware: true },
});
```

```jsonc
// package.json
{
  "scripts": {
    "lint": "oxlint",
    "lint:fix": "oxlint --fix",
  },
}
```

Three anti-slop rules skip a value at its boundary. `no-runtime-typeof` also counts a `.js`/`.mjs` function documented `@returns {x is T}` as a type guard. `no-unsafe-dictionary-type` allows `Record<string, unknown>` as a `value is T` target or inside a type-guard body. `no-unknown-parameters` skips a `this` parameter, a parameter decorated `@JSONBody`, `@JsonBody` or `@Parameter`, the reason of a callback passed directly to `.catch(...)` or as `.then(_, onRejected)`, the parameter of a `(reason: unknown) => void` type declared as `reject` or on a `new Promise` executor, and a validator's input that the body narrows before any other use: every read is the argument of a call that is the whole test of an `if` or `?:` or the left operand of an `&&` or `||`, the argument of a schema's `.decode`, `.parse` or `.safeParse`, or inside the branch such a guard call makes true.

`no-unknown-parameters` reads only the written annotation, and oxlint plugins get no type information, so a parameter typed with an alias or indexed type that resolves to `unknown` (such as `Parameters<typeof f>[0]`) passes. The convention: annotate a parameter with a concrete type, or with the boundary decode that narrows it, and never with an alias that resolves to `unknown`. Reviewers treat such an alias as `unknown` and reject it.

`require-safety-comment-for-type-assertion` asks for a `SAFETY: <reason>` comment on every type assertion (`as`, `<T>x`, and a JSDoc cast in `.js` files) and on every non-null assertion (`x!`); `as const` needs none. Put the `SAFETY:` comment immediately before the assertion or before its innermost containing statement; a comment above an enclosing `if` or block does not cover an assertion inside it.

`no-runtime-typeof` also reports a `typeof` that only fills in the text of a message, such as ``throw new Error(`received ${typeof value}`)`` or ``assert(ok, `received ${typeof value}`)``: one file cannot see what catches, compares or records the message.

No rule warns. oxlint reports `correctness` as warnings by default, and warnings never fail the command, so the preset raises it to error.

Import sorting is off because it moves value imports across side-effect imports, and in an AntelopeJS module `import "./components"` is what registers the decorated classes. Turn it on only where import order does not matter.

### Options

```ts fragment
antelopePreset({
  antiSlop: false, // true (default)
  guardrails: false, // true (default)
  importCycles: false, // true (default)
  complexity: { maxParams: 8 }, // override thresholds, or false
  importSorting: true, // false (default); needs eslint-plugin-perfectionist
  typeAware: false, // true (default); false when the repository has no oxlint-tsgolint
});
```

`oxlint-tsgolint` reads only TypeScript files, so the type-aware rules do not run on the script blocks of `.vue` files, and oxlint reports nothing about it. `antelopeNuxtConfig({ typeAware })` runs the same rules there from ESLint; see [ESLint](#eslint-nuxt-front-ends).

### Add ignore patterns

oxlint reads `ignorePatterns` only from the root config, never from `extends`, so the synced `oxlint.config.ts` sets `ignorePatterns: ANTELOPE_IGNORE_PATTERNS`, and sync replaces the earlier template that did not. `ANTELOPE_IGNORE_PATTERNS` holds generated output and what sync writes under the agent directories: the synced files of each writing skill and its `.claude/skills` link. The repository's own files under `.agents/` and `.claude/` are linted. oxlint skips `node_modules` only when a `.gitignore` or the root config's `ignorePatterns` leaves it out, so a root config without the shared patterns, in a project with no `.gitignore`, makes a bare `oxlint` lint every dependency file with the type-aware rules. Spread the shared patterns when adding your own:

```ts
// oxlint.config.ts
import { defineConfig } from "oxlint";
import {
  ANTELOPE_IGNORE_PATTERNS,
  antelopePreset,
} from "@antelopejs/tooling-configs/oxc/lint";

export default defineConfig({
  extends: [antelopePreset()],
  ignorePatterns: [...ANTELOPE_IGNORE_PATTERNS, "playground/**"],
});
```

## Guardrail pack

Onboard a repository with one command at its root. The repository needs a `package.json` and a git remote on GitHub.

```bash
pnpm dlx --package=@antelopejs/tooling-configs antelopejs-sync --init
npx --package=@antelopejs/tooling-configs antelopejs-sync --init
```

`--init` adds `node_modules` to `.gitignore` and declares each of `@antelopejs/tooling-configs`, `oxlint`, `oxlint-tsgolint` and `oxfmt` the repository does not declare yet. In a pnpm or npm workspace, it sets each member's declared pack tools to the root's ranges, so the workspace installs one copy of the pack. A root `catalog:` spec is copied as written. A member `catalog:` spec is kept when its catalog entry, in `pnpm-workspace.yaml` or Bun's root `package.json`, matches the root's range, and otherwise `--init` names the member and the package and stops before installing. It also moves the `options` of a member's oxlint config, which oxlint accepts only in the root config, to the same flags on the member's `oxlint` scripts. It stops before installing when an option has no command-line flag. It installs with the repository's package manager, runs `antelopejs-sync`, installs again when sync added devDependencies, and formats `package.json` with the installed oxfmt. It takes the full profile only and rejects `--check` and `--profile template`. Install output shows only when the install fails.

It then sets `delete_branch_on_merge` through `gh` when it can, even when an earlier step failed. When `gh` is missing, unauthenticated or refused, `--init` prints the `gh api -X PATCH repos/{owner}/{repo} -F delete_branch_on_merge=true` command to run and exits 1. After any failure, fix what it printed and rerun `antelopejs-sync --init`. Commit and push to the default branch afterwards, so the first run reports `verdict` and `ci / checks`.

Every step is idempotent: a second run changes nothing. Plain `antelopejs-sync` also runs from a repository that already has the devDependencies installed:

```bash
pnpm exec antelopejs-sync
pnpm install
```

Sync sets `minimumReleaseAge: 1440` and lists `@antelopejs/*` under `minimumReleaseAgeExclude` in a pnpm repository's `pnpm-workspace.yaml`, and in the `pnpm-workspace.yaml` of each folder with its own `pnpm-lock.yaml`, and of each `playground` with a `package.json` that no workspace above lists, before its first install: pnpm installs that folder as a workspace of its own and does not read the root's file. It writes these nested files in a repository whose root npm installs too, there only in folders pnpm installs: one with a `pnpm-lock.yaml`, or a playground with no lockfile and no `package-lock.json` above it. A root that sets no `packageManager` counts as pnpm's unless it holds a `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`, `bun.lock` or `bun.lockb` and no `pnpm-lock.yaml`. It raises a lower age, and puts `@antelopejs/*` in place of the `@antelopejs/interface-*` pattern it listed before. It quotes the strings it writes in single quotes when the nearest Prettier config of that folder (a `package.json` `prettier` key, `.prettierrc`, `.prettierrc.json`, `.prettierrc.yaml` or `.prettierrc.yml`) sets `singleQuote: true` at its top level, and in double quotes otherwise, as for a config in another format, so a new file passes that folder's `prettier --check`. The age keeps pnpm from installing a release published less than a day ago, so a broken release is pulled or fixed before an install locks it. pnpm before 10.17.0 installs such a release whatever the file says, so sync fails until `packageManager` pins 10.17.0 or later. Without the exclusion, pnpm resolves each range to an interface release more than a day old where the range admits one, so an install in the day after an interface release locks two copies. In a repository with any of these folders, checks also runs `pnpm:release-age`. It fails when one of their `pnpm-workspace.yaml` files is missing, sets `minimumReleaseAge` below 1440 or not at all, or does not list `@antelopejs/*` under `minimumReleaseAgeExclude`, and names the file. When a tracked `package.json` declares an `@antelopejs/*` package, it also runs `dependency:ranges` (see [Dependency ranges](#dependency-ranges)), which reads the manifests, and from the registry the `latest` dist-tag of each `@antelopejs/interface-*` package they take and the newest release of each DMS module. On the `fast` and `full` tiers, which the shared CI workflow sets in `ANTELOPEJS_CI_TIER` for a pull request (the legacy `draft` tier is skipped the same way), it skips `lockfile:module-peers`, `dependency:ranges`, `readme:version` and `published:types`, the steps that read the registry, and counts them as skipped; the `queue` tier, the merge queue's `merge_group` run, the `nightly` tier and a run with no tier run all four. In a git checkout it also runs `git:identity`, which fails when the repository's own git config, the `.git/config` every worktree shares or a worktree's `config.worktree`, sets `user.name` or `user.email`, and names the file and value. An identity from the global config or a `git -c` passes. When the `README.md` of the root or of a workspace package holds a config example whose `package` is an `@antelopejs/*` package, such as `source: { type: "package", package: "@antelopejs/brevo", version: ">=0.0.9 <0.1.0" }`, it also runs `readme:version`. It fails when that example's `version` range does not stop below the next minor of the package's newest version and admit it, as [Dependency ranges](#dependency-ranges) reads a range, and names the README line and the range to use. The newest version of a package of the repository is the `version` in its `package.json`. For any other package it is the `latest` dist-tag on the registry npm is configured with, and the step fails when it cannot read it. A value that is not a range, such as `latest`, passes. When the root or a workspace package is not `private` and names declarations through `types`, `typings` or `exports`, it also runs `published:types`, after `test` and alone. It runs each such package's `prepack` through `pnpm run` or `npm run`, then packs it with lifecycle scripts off, so `prepare` and `postpack` do not run. It installs the tarball alone in a scratch folder without install scripts, together with the package's peers (optional ones included), `typescript` and `@types/node`, both at their latest version unless the package names them as peers. A workspace package it depends on comes from that package's own tarball, not from the registry. Then it runs `tsc` with `skipLibCheck: false`, `strict` and `nodenext` resolution over a file that imports each entry the package's `exports` names, a `*` subpath once per shipped file it matches. A package without `exports` gets its bare name and every declaration file it ships instead. The step fails on any error and names each file as `<package>/<path>`. An error inside the declarations of a dependency the repository does not publish, which the repository cannot fix, is declared in `guardrails.published-types.json` at the root, by the dependency, the file inside it and the code tsc prints:

```json
{
  "knownFailures": [
    {
      "dependency": "rethinkdb-ts",
      "file": "lib/response/cursor.d.ts",
      "code": "TS2416"
    }
  ]
}
```

An entry matches every error with that code in that file, at any line. The step prints each matched error under `errors guardrails.published-types.json declares as known` whether it passes or fails, and passes when every error it found is declared. An error in a package of the repository, or in a file or with a code no entry names, still fails, and an entry may not name a package of the repository. Once tsc ran over every package, an entry that matched no error fails with `<dependency>/<file> <code> no longer occurs. Remove the entry.`, so the entry goes when the dependency fixes its declarations. When the step runs, a malformed file, an entry with a path tsc does not print (such as `./lib/x.d.ts`) or a repeated entry fails it before anything is packed. It needs the registry, so it fails offline unless the package manager's store already holds what the install needs.

`ANTELOPEJS_CHECKS_SKIP` accepts the name of any step.

The steps run at the same time, then `suppressions` and `test` last, each alone, so a `lint` that regenerates the types a tsconfig extends, as a DMS `lint` rewrites `.dms-types`, never empties them under the type-aware oxlint run of `suppressions`. When `typecheck` writes files, it runs first and the other steps start after it, so `lint` never resolves a workspace package's `dist` that `typecheck` is rebuilding. `typecheck` writes files when the scripts it runs reach a `build` script or a `tsc` that leaves `noEmit` unset on its command line and in its tsconfig chain, following `--filter`, `--dir` and `-r` into workspace packages. A package-manager target it cannot resolve, such as a `--dir` read from a variable or a dependency `--filter` like `pkg...`, counts as writing. A build that a wrapper script runs, such as `node scripts/run.mjs pnpm build`, is not seen. When a wrapper hides the build, or two other steps share what one of them builds, add a `checks:prepare` package script that builds it. `pnpm run checks` runs it once before any step and after it checks that Docker Compose can run, whenever at least one step runs. Its output is printed only when it fails, and then no step runs. It counts as a step only when it fails, and a repository without it runs as before.

When the repository has `.github/compose.yml`, the file the shared CI starts through its `services-compose-file` input, and the `test` step runs, `pnpm run checks` runs `docker compose -f .github/compose.yml up -d --wait` before the steps and `docker compose -f .github/compose.yml down -v` after them, also when a step fails or the run is interrupted (SIGINT, SIGTERM or SIGHUP stops the running step or `up`, removes the services and exits 130, 143 or 129; a repeated signal does not cut the teardown short). The compose project is `COMPOSE_PROJECT_NAME` when set, else the file's own `name:`, else one named after the repository root, so checkouts never share the `github` project compose would derive from the file's directory. Services are left alone when every port the file publishes already accepts connections, so a stack you started yourself is reused and kept. A run's project that already had containers before the run is started but not removed. When Docker Compose cannot run, the run fails before any step, naming the compose file, because the tests that need those services would wait for them forever. On GitHub Actions (`GITHUB_ACTIONS=true`) the workflow owns the services, and `--no-services` skips all of this anywhere.

### Module locks

A repository that commits `antelope-lock/` installs each module from its recorded lock, so its modules and their dependencies move only when someone records the locks again. Renovate does not read `antelope-lock/`, so `AntelopeJS/.github` ships the pieces that keep the locks current:

- `module-locks-refresh.yml`, the shared workflow that records the locks again and opens or updates the pull request that carries them.
- `module-locks: true`, the input of the shared CI workflow that checks the committed locks.
- `module-locks-renovate.yml`, the workflow that refreshes the locks on the pull requests Renovate opens.

`antelopejs-sync` does not write these callers. Add them to each repository that commits `antelope-lock/`; the inputs, the caller to copy and the failure rules are in the `AntelopeJS/.github` README.

### Hand-written CI jobs

A job of `.github/workflows/ci.yml` with no job-level `uses` is a hand-written job. In a workflow that calls ci-node.yml, `antelopejs-sync` keeps each of them to the org's CI conventions, and a second run changes nothing.

- Runner. The runner is chosen when the job runs, from the repository's visibility: `${{ vars.RUNNER_CI || (github.event.repository.visibility == 'public' && 'ubuntu-latest' || 'blacksmith-4vcpu-ubuntu-2404') }}`, with `RUNNER_CI_WINDOWS`, `windows-latest` and `blacksmith-4vcpu-windows-2025` for Windows. An event without the visibility lands on Blacksmith. A literal label becomes the expression of its OS, and so does an expression made only of `vars.<name>` and `'literal'` terms joined by `||`, by its last literal. A `${{ matrix.os }}` runner becomes `${{ matrix.os == '<the matrix's Windows label>' && (<Windows choice>) || (<Linux choice>) }}` when sync can list every leg: a literal `os` list and literal include items, one label per OS. The list stays as it is, so every comparison and `exclude` on its labels keeps matching. A generated `os` or `include`, or a label that is an expression, could add a leg sync cannot see, so the job stays with an advisory that says why. A ternary on `matrix.os` against a Windows or a Linux label becomes the same ternary on that label, which keeps every leg on the OS it had. Any other runner stays, and sync prints `Runner: .github/workflows/ci.yml job <id> runs on <value>, ...` as an advisory.
- Actions. Each `uses` of `actions/checkout`, `setup-node`, `cache` (and `cache/restore` and `cache/save`), `upload-artifact`, `download-artifact`, `create-github-app-token` and `setup-java`, and of `pnpm/action-setup`, is pinned to the commit this package carries, with its release as the trailing comment (`# v7.0.1`). Other actions stay.
- Concurrency. A workflow on `pull_request` with a hand-written job that is not an aggregator, a job with `needs` and no step that uses an action, gets a top-level `concurrency` whose `cancel-in-progress` is `${{ github.event_name == 'pull_request' }}`. A different `cancel-in-progress` is replaced and nothing else of the block is touched.
- Formal checks. A folder `.agents/skills/formal-*` with a `check.mjs` is a formal skill, and the `formal-checks` input of the `ci` caller lists each one, sorted, unless a job left in the file runs it. A formal job that only sets up Node, Java and a cache and runs `check.mjs`, and that no other job needs, is deleted and removed from every `needs`; an `extra-commands` line that only runs a `check.mjs` leaves that input. An entry keeps its `run` and takes its `paths` from the table rows under the `Coverage record` heading of the skill's SKILL.md, else under `Scope and assumptions`. When a file named there is missing from the repository or matches several, or the record names a glob, a folder or a file that is not source code, the entry has no `paths` and the check runs on every pull request. An existing entry whose skill has no folder stays as it is. A formal job that does more than set up stays, and so does its skill's entry out of the input.
- Gate. `ci` needs no hand-written job, so lint, typecheck and tests report without waiting for an e2e suite. The `verdict` job sync writes needs every job with `ci`, and so may an aggregator of the repository such as `ubuntu`. One of them must be a required check. Sync prints one `Gate: .github/workflows/ci.yml jobs <ids> run beside the ci caller, ... <aggregator> needs them with ci, so require <aggregator> in the ruleset, ...` advisory. It names the first aggregator that needs `ci` and every listed job and runs under `always()` or `!cancelled()`, else `verdict`: a required job skipped by a failed need reports success.
- Gate unwiring. A `ci` caller that runs under `if: ${{ !cancelled() && !contains(needs.*.result, 'failure') && !contains(needs.*.result, 'cancelled') }}`, as the former `gateHandJobs` profile wrote it, loses every hand-written job it does not read as `needs.<id>` from its `needs`, and loses that `if` once its `needs` is empty. Under that wiring a failed job skips `ci`, and a skipped caller of a reusable workflow never reports `ci / checks`, so the merge queue waits for its timeout instead of failing.

Advisories print under `antelopejs-sync` and `antelopejs-sync --check` and never fail either. A rewrite is drift, so `--check` fails with `Drift: .github/workflows/ci.yml`.

### Lib check coverage

No repository sets `skipLibCheck` globally. `typecheck` runs a full `tsc --noEmit` over the program that covers the sources, and `build` may pass `--skipLibCheck` only over a program `typecheck` checks in full, so nothing `typecheck` skipped goes unchecked. `antelopejs-sync --check` fails with a line naming the file, the script and the fix, and plain `antelopejs-sync` prints the same line as a `Note:` and carries on, when:

- `build` passes `--skipLibCheck` (in any letter case) to a `tsc` program (`-p`/`--project`, `tsconfig.json` when absent) that no `tsc` run of `typecheck` covers without `--skipLibCheck`. `./tsconfig.build.json` and `tsconfig.build.json`, `-p .` and no `-p` are the same program. `pre<script>` scripts count with their script, and `&&` chains, parentheses, `cross-env` and environment prefixes, `run-s` and `npm-run-all`, and scripts run through `pnpm`, `npm`, `yarn` or `bun` (`--filter <x>`, `-C <dir>` and other options with a value included) are followed to five levels. `tsc` is recognised as `tsc`, `npx tsc`, `npx -p typescript tsc`, `pnpm exec tsc` and `node ./node_modules/typescript/bin/tsc`. `antelopejs-tsc` is recognised wherever `tsc` is: on its own, through `npx`, `pnpm exec` or a package manager, and as `node_modules/.bin/antelopejs-tsc`.
- A tsconfig the scripts use through `tsc`, or the root `tsconfig.json`, ends up with `compilerOptions.skipLibCheck: true`, set directly or through a local `extends` chain (`.json` or `.jsonc`, a later duplicate key winning as in tsc). `tsc -b` reads the config it names and the projects they reference. Presets extended from a package are not read. When the file that sets it is one git ignores, such as Nuxt's generated `.nuxt/tsconfig.json` or the `.dms-types` tree of `ajs dms prepare-types`, nothing is reported: the value comes only from a generated file, whose third-party declarations no repository owns.
- A `release` script exists and does not run `typecheck`, directly or through a script it runs, its `prerelease`, or a release-it hook that runs before publishing (`before:init`, `before:bump`, `before:release` and their plugin-scoped forms), read from `.release-it.json` and from `release-it.hooks` in `package.json`.
- A file the check needs cannot be read (a directory where a tsconfig is expected, a permission error): both commands print a `Note:` that says "could not read …" and neither fails on it.

`antelopejs-checks` runs `sync:check`, so a finding fails it too.

Known blind spots, none of them read: `|| true` or a background `&` after a `typecheck`, a `typecheck` placed after `release-it` in `release`, a `typecheck` that checks nothing, `vue-tsc`, release-it configs other than JSON (`.release-it.js`, `.yaml`, `.toml`), presets extended from a package, and workspace packages.

### Test timeout

Every repository runs its tests on one timeout, 30,000 ms per test and per hook, under mocha and vitest alike. It is `TEST_TIMEOUT_MS` in `src/test-timeout.ts`, and a release that changes it reaches every repository through the checks below.

- mocha: `ajs module test` builds its mocha run in code and reads no `.mocharc`, so the timeout travels as a flag. `antelopejs-sync --check` fails, and plain `antelopejs-sync` prints a `Note:`, for each `ajs module test` or `mocha` run in the scripts of the root `package.json` and of every workspace member that does not pass `--timeout 30000` (`--timeout=30000`, and mocha's `-t 30000`, also count). Runs are found through `pnpm exec`, `npx`, a package manager running the bin (`pnpm mocha`), `&&` chains and environment prefixes, as in [Lib check coverage](#lib-check-coverage), behind `c8` or `nyc`, and as `node` running `mocha`, `_mocha` or `mocha.js` by path. The flag is read as written, the last one winning, so `--timeout 30s` is reported. A run without the flag is on mocha's 2000 ms default or, for a plain `mocha`, on a `.mocharc` limit. Plain `antelopejs-sync` writes the flag into those scripts: it sets each timeout flag's value to 30000, or adds `--timeout 30000` after the run's last word, or right after the runner when the words after it hold a `$(…)` substitution, a backtick, a backslash or a redirection, and changes nothing else. It leaves a run alone, with its `Note:`, when its quotes do not pair up, it passes `--`, a timeout flag has no value, or a flag needs changing in a part with that shell syntax. `ajs module test` takes `--timeout` from `@antelopejs/core` 1.23.1, and 1.23.0 rejects it as an unknown option. So both modes fail, and write nothing, while a manifest that runs `ajs module test` runs an `@antelopejs/core` before 1.23.1: the version the root `pnpm-lock.yaml` locks for it, else the `version` of the `@antelopejs/core` installed in the manifest's `node_modules` or the root's, as an npm or yarn repository has it, else the lowest release its `dependencies` or `devDependencies` range admits, or, when it declares none, the root `package.json` range. The error names the manifest and the locked version, the installed one or the range, and says to set it to `>=1.23.1` or later. A spec that is not a semver range, such as `workspace:*`, passes.
- vitest: spread `testTimeouts` into the config's `test`. Projects declared with `extends: true` inherit it. The lint rule `antelopejs/shared-test-timeout` fails a `vitest.config.*` that sets `testTimeout` or `hookTimeout` itself, or never uses `testTimeouts` from the preset (a bare or type-only import does not count).

```ts fragment
import { testTimeouts } from "@antelopejs/tooling-configs/vitest";
import { defineConfig } from "vitest/config";

export default defineConfig({ test: { ...testTimeouts } });
```

A suite that needs a longer limit by design, such as a browser journey that boots a whole stack, sets it with an `oxlint-disable-next-line antelopejs/shared-test-timeout -- <reason>` directive, which the [suppression budget](#suppression-budget) counts. Per-test `this.timeout()` and `vi.setConfig()` calls are not read, and neither are a package that runs vitest with no `vitest.config.*` file, a `test` block in `vite.config.*`, or a `--testTimeout` flag. A `vitest.config.*` that only extends a shared base file through `mergeConfig` is reported even when the base spreads `testTimeouts`: spread it in the file vitest loads.

### TypeScript 7 for build and typecheck

A repository keeps TypeScript 6 as its `typescript` package and can build and type-check with TypeScript 7, the native compiler. The pack lists TypeScript 7's native compiler packages, `@typescript/typescript-<platform>-<arch>` at `~7.0.2`, as optional dependencies, so the package manager installs the one for the platform it runs on, and `antelopejs-tsc` runs that compiler with its arguments unchanged. Installing the pack leaves the repository's `tsc` the one its own `typescript` ships, whatever its version, under npm, pnpm, yarn and bun. npm links into `node_modules/.bin` the `tsc` of a package at the root of `node_modules`, the first in name order when several ship one, so a package that ships a `tsc` under another name than `typescript` can replace the repository's. The pack installs none: its compiler packages have no bin, and its TypeScript 6 is a plain `typescript` dependency, which the package manager may share with the repository's `typescript` when that one satisfies `^6.0.2` and otherwise installs under the pack, never in the root `typescript` the repository owns. An override of `typescript` in the repository (`overrides` under npm, bun and pnpm, `resolutions` under yarn) reaches the pack's dependency too; the pack's commands then stop with a message that names the version found and the scoped override that exempts the pack, such as `"overrides": { "@antelopejs/tooling-configs": { "typescript": "^6.0.2" } }` under npm. Under yarn 1 the exemption, `"**/@antelopejs/tooling-configs/typescript": "^6.0.2"`, must come before any other `resolutions` key that matches `typescript`, because yarn 1 applies the first one that matches.

To opt in, call `antelopejs-tsc` in place of `tsc` in `build` and `typecheck`, with the same arguments. To back out, call `tsc` again.

```json
{
  "scripts": {
    "build": "antelopejs-tsc",
    "typecheck": "antelopejs-tsc --noEmit"
  }
}
```

Before opting in, remove from the tsconfig chain the options TypeScript 6 deprecated: `baseUrl`, `moduleResolution` set to `node`, `node10` or `classic`, `target` set to `es5`, `downlevelIteration`, `outFile`, `module` set to `amd`, `umd` or `system`, and `esModuleInterop`, `allowSyntheticDefaultImports` or `alwaysStrict` set to `false`. TypeScript 7 refuses each one with an error that names it, such as `error TS5102: Option 'baseUrl' has been removed`, and exits non-zero. `ignoreDeprecations: "6.0"` does not bring them back.

Only `build` and `typecheck` change. TypeScript 7.0 ships no compiler API, so everything that loads one stays on TypeScript 6: the `antelopejs` lint rules, `antelopejs-api-diff`, `antelopejs-comment-proof`, the auto-import checks and dts-bundle-generator load the pack's own `typescript` 6 dependency, and vue-tsc, `nuxi typecheck`, ts-node and editors use the repository's `typescript`. Sync reads `antelopejs-tsc` wherever it reads `tsc`, so [Lib check coverage](#lib-check-coverage) holds for a repository that opted in.

Known differences between the two compilers' output:

- JavaScript is the same, except for a class that names itself in one of its member decorators: TypeScript 7 emits a `<Name>_1` alias assigned in a `static {}` block where TypeScript 6 names the class.
- Declarations describe the same types. Without `stableTypeOrdering`, TypeScript 6 can print union members in another order. With `stableTypeOrdering: true` in the tsconfig, which TypeScript 7 accepts, the order matches, and what remains is a type one compiler prints through an alias and the other spells out, such as `value is string` for `value is TypeofTags["string"]`.
- Source maps differ.

`antelopejs-api-diff` emits both revisions' declarations with TypeScript 6 from the repository's tsconfig, so it reports any change to the API between them whichever compiler builds the package. It does not compare those declarations with the ones TypeScript 7 ships; `stableTypeOrdering` brings the two to the same order. Its runtime check runs the package's `build`, so it compares the JavaScript TypeScript 7 emits once the repository opted in.

### Suppression budget

`guardrails.suppressions.json` caps the suppressions in authored code files. It is permanent: it stays when its counts reach zero.

```json
{
  "rules": { "anti-slop/no-chained-type-assertions": 19, "*": 0 },
  "tsExpectError": 8,
  "tsIgnore": 0,
  "safety": 2,
  "config": { "typescript/unbound-method for src/test/**": 1 }
}
```

- `rules` holds lint directives (`oxlint-disable`, `eslint-disable`, their `-line` and `-next-line` forms, in line or block comments, after code too) per rule they name; a directive naming several rules counts once per rule, and one naming none counts under `*`. A rule missing from `rules` has ceiling 0. The other fields count `@ts-expect-error`, `@ts-ignore` and `SAFETY:` comments. The counter is the one behind the proof tables: it reads comments from the parser, so strings and template literals are never counted, and it skips generated output as the size guard does.
- `config` holds the rules a lint config switches off, to `allow` or to a warning, keyed `<rule> for <glob>`: in `oxlint.config.*`, `.oxlintrc.json`, `.oxlintrc.jsonc` and `eslint.config.*` at any depth, every `rules` and `categories` map (a category as `category:<name>`) and an ESLint composer's `overrideRules` argument, one key per glob of the block's `files` (`*` when it has none). A nested config's globs are anchored at its directory and its blocks without `files` are `<dir>/**`, so a rule-off moved between config files is a new key. Rule maps, severities and globs held in same-file variables or spread from them count where they are used; the pack's presets are not in the file, so they never count. A glob is a key of its own, so adding, widening or renaming a glob, deleting `files`, or moving an override's rules to the top level creates a key at ceiling 0 and fails. Narrowing or splitting a scope is burn-down: a key may use the room a same-rule key whose glob contains its glob gives up (`*`, `**` and `**/*` contain every glob; a single-segment `*` never contains `**`; other glob syntax counts only when equal), in the full, staged and base checks, and `--update` moves that ceiling to the narrower key. A scope split into several narrower globs gives each the old ceiling, so the `config` total can rise while the files it covers do not; read totals per key, not as a measure of scope. `.` and `..` segments count only when equal. A failure names the fix: delete the entry and fix the code its rule reports, or put the exception on the line that needs it as a directive with a reason. A config entry switching off a rule no directive may name fails as an added directive does. Sync adds `config` at today's counts to a budget that predates it; until then config rule-offs are not capped.
- `agentFiles` is `true` once the budget counts the repository's own files under the agent directories (`.agents/`, `.claude/` and the others), skipping only what `antelopejs-sync` writes there, which is what lint skips. A budget without it counts none of them, so upgrading fails nothing: `antelopejs-sync` adds each key's count in those files to its ceiling and sets the field. `antelopejs-suppressions --base` allows that one rise on a base without the field, by no more than the count in those files at the base per key (a directive the same branch adds there is not adoptable), and fails a budget that drops the field once the base has it.
- `antelopejs-suppressions` fails when a count is above its ceiling, printing each `file:line` in the files the change touched and the fix: fix the code, or remove another suppression of the same kind; a rule that keeps needing suppressions should be changed in the preset. It prints nothing on success.
- `antelopejs-suppressions --update` lowers each ceiling to the current count and drops each `rules` and `config` key that suppresses nothing; a missing key has ceiling 0. No command raises a ceiling.
- `SAFETY:` comments and directives disabling `anti-slop/require-safety-comment-for-type-assertion` share their room: a `SAFETY:` comment may use what those directives leave below their ceiling, in the full, base and staged checks, and `--update` moves that room to `safety`. Replacing such a directive with a `SAFETY:` comment needs no raise; their sum never rises.
- `antelopejs-suppressions` also compares the budget with the one on the pull request base: `--base <ref>` when given, else the `GITHUB_BASE_REF` branch in CI (fetched from `origin` into a shallow checkout), else `origin/HEAD`. It fails when a ceiling is higher than on the base or the budget drops the `config` the base has, so a raise merges only through the operator's ruleset bypass. A removed key is a ceiling of 0, so removing one that still suppresses something fails the ceiling check unless a containing scope of its rule lends it room. A base without a budget, a first adoption, passes. Without a base the comparison is skipped.
- `antelopejs-suppressions --staged` compares the suppressions in the staged files with those files at HEAD, following renames and counting deleted files, and fails a kind that rises by more than the staged budget raises its ceiling. A suppression moved between staged files nets out.
- `@ts-ignore` is also a lint error (`typescript/ban-ts-comment`); `@ts-expect-error` fails once its error is gone.
- Both modes also fail a lint directive in a file the change touches that suppresses nothing, whether the directive was added or already on the base: one extra `oxlint --report-unused-disable-directives` run over the touched files that contain a directive, under the repository's own lint configuration, so a directive for a rule the preset does not run is dead. A dead directive fails with its `file:line`, naming the rule to drop when the directive names several, or telling you to delete it. Touched files are the staged files with `--staged`, and in the full check the working tree against the merge-base with the pull request base (the base itself when there is no merge-base, as in a shallow checkout), untracked files included, or against HEAD without a base. A file the change does not touch is not read, so upgrading the pack fails no existing file; its dead directives surface when a change next touches the file. `eslint-` directives in a directory with an ESLint config are left to ESLint, and `.vue` files are not read by oxlint. When a tsconfig cannot load, oxlint runs no type-aware rule on the files it covers, so the check judges no directive of the run for a type-aware rule, in its `typescript/`, `@typescript-eslint/`, `typescript-eslint/` or `eslint-plugin-typescript/` name, or for no named rule, since a tsconfig's `references` reach past its directory, and prints a note naming the tsconfig, its error and each directive it left unjudged. Deleting a dead directive lowers the budget: run `suppressions:update`.

### Size

`antelopejs-check-size` fails on an authored file over 20,000 bytes, tests included. The repository's own files under the agent directories count; the files `antelopejs-sync` writes there (the `SYNCED_AGENT_PATTERNS` that lint skips) do not. Generated code (`dist`, `coverage`, `.nuxt`, `.output`, and `build` or `output` at the repository root or a package root, never under `src/` or `test/`), fixtures, lockfiles, `CHANGELOG.md`, Markdown and binary assets are excluded. JSON is data, never code: every `*.json`, `*.jsonc` and `*.json5` file is excluded, wherever it lives. Lint and format still cover it. Files over the limit with a NUL byte in their first 8,000 bytes are binary even without a known extension. Staged checks inspect the index blob.

Pass paths to check only those files. The command also fails on an `oxlint-disable` or `eslint-disable` directive (line, next-line or file form) that names no rule: oxlint applies such a directive before any rule runs, so `no-comments` cannot report it. It reads real comments only, with the same counter as the proof tables, so directive text inside a string is not reported.

### Cleanup proof

A behaviour-preserving cleanup PR shows `antelopejs-api-diff <base-ref>` passing. It checks each tracked package with a `tsconfig.json` that publishes something (not private, and declaring `exports`, `main`, `types`, `typings` or `typesVersions`) and lists the others as `API: skipped <directory>, <reason>.`. Each package is analysed and bundled with the pack's own TypeScript 6, its `typescript` dependency, never a `typescript` of another major the repository installs, so a repository on TypeScript 7, which has no compiler API, is proven like any other. The package's config is read as the TypeScript it installs reads it: on TypeScript 5, each option whose default TypeScript 6 changed (`strict`, `alwaysStrict`, `types`, `module`, `moduleResolution`, `esModuleInterop`, `allowSyntheticDefaultImports`, `noUncheckedSideEffectImports`, `target`) keeps its TypeScript 5 default when the config leaves it unset, the options TypeScript 6 deprecated, such as `baseUrl`, still compile, and the output is laid out under the common directory of the sources when no `rootDir` is set. A package that declares `typescript` but cannot resolve it fails with an execution error naming the package and asking for an install, because the pack cannot tell which defaults it builds with; one that declares none is read with TypeScript 6's defaults. Large packages are bundled by several worker processes (up to 8, bounded by cpus and free memory); the output is the same as a single process. It emits declarations without comments, resolves published entries from `exports` (preferring `types`), `main`, `types`/`typings` and `typesVersions`, and bundles each entry's local declaration closure. External packages stay external. The bundles of both revisions are compared as one `declarations.d.ts`: an index of every published entry, then each distinct declaration text once, under one `// In` line per entry that carries it (`// In every entry` when all do). A change shared by many entries is printed once. The first hunk that changes a declaration below its `// In` lines names its entries in the hunk header, and an added or removed entry prints one index line and one `// In` line per declaration it shares. Stable top-level ordering ignores declaration moves between internal files while preserving overload order. Members of object type literals, interfaces and classes are compared in a canonical order, because TypeScript can emit an inferred object type's properties in another order after a refactor; overloads, call and construct signatures, tuple elements, parameters, enum members and union constituents keep their written order. Compiler errors fail the proof.

A comment-only PR shows `antelopejs-comment-proof <base-ref>` passing instead of a verifier. It includes private packages, ignores type diagnostics and compares comment-free JavaScript emit byte for byte. Both commands exclude test sources, fail on added or removed outputs, and print unified diffs for changes.

The runtime half loads each built entry in a child process and writes its description to a file, so an entry that prints on import, such as a CLI under a wildcard export, is described like any other. An entry that exits while it loads, or sets a non-zero `process.exitCode`, has its exit code recorded (`"exit": 2`), so a changed exit code is a difference. An entry that throws, while it loads or afterwards, is an execution error.

Test-helper entries are outside both halves. A published entry whose built file is test output relative to `outDir` (under `test/`, `tests/` or `__tests__/`, or named `*.test.*` or `*.spec.*`) is neither bundled nor loaded, because helpers such as `./tests/*` import a test runner that the proof does not run. This applies the same way to the declaration and the runtime half, to wildcard and plain targets, and to files a general wildcard such as `./*` matches. Each half prints `API: skipped test-helper entry <target> in <directory>` or `Runtime API: skipped test-helper entry <target> in <directory>`; a package whose only wildcard export is `./tests/*` still has its other entries compared in both halves.

Pass `--allow-added <glob>` (repeatable) to `antelopejs-api-diff` when a refactor adds helper files that a wildcard export publishes, such as an `internal/` directory under `"./*"`. An added entry passes, in both the declaration and the runtime half, when its published subpath matches a glob (for example `--allow-added '**/internal/**'`, matched against `base/table-view/internal/helper` for `./base/table-view/internal/helper`) and its source module is marked `@internal`: a leading `/** @internal @packageDocumentation */` comment on the module (`@module` and `@fileoverview` also qualify), or an `@internal` tag on every exported declaration. Allowed entries are printed under `Added (allowed): <count>`; nothing is printed when no entry was added. An added entry that matches but is not marked `@internal` fails with the file and the fix. Added entries matching no glob, removed entries and changed entries still fail, matching or not. Without the flag nothing changes.

```bash
pnpm exec antelopejs-api-diff origin/main --allow-added '**/internal/**'
```

Pass `--skip-runtime <glob>` (repeatable) when a package publishes a script that throws or never settles on import, such as a build or server script under a wildcard export. The runtime half does not load an entry whose published subpath matches a glob, in either revision, and prints `Runtime API: skipped entry <subpath> in <directory>, which --skip-runtime names.` for each one. The declaration half still compares it when the package publishes declarations for it; a script with none is left out of both halves, so an added, changed or removed one shows only as its skip notice. A wildcard export is resolved from the directory before its `*`, inside the package, and never from a `node_modules` directory, since Node does not resolve a subpath through one.

```bash
pnpm exec antelopejs-api-diff origin/main --skip-runtime 'templates/vue/server.mjs'
```

A DMS frontend module publishes more than its package entries: every export of a file under a directory its `dms.frontend.build.ts` passes to `registerAutoImports` is auto-imported into every frontend module, `@internal` or not, and the package itself is usually private. For each tracked `dms.frontend.build.ts`, the proof reads the declared directories (string literals only; anything else is an execution error naming the form to write), drops `app/build/` and directories outside the module as `@antelopejs/dms-frontend` does, and lists one `<name> (value|type): <signature>` line per auto-imported name under `Auto-imports:`. Names are read statically with the module's TypeScript, which resolves `export *` and the `#<layer>/*` aliases; no Vite build runs. Each scanned module is typed with the imports unimport would inject for the names it uses without importing them: dms-frontend's `templates/vue/frontend-module.ts` exports, `vue`'s exports and the module's own auto-imports. A composable returning `ref<T>()` or `useDmsState<T>()` therefore prints `T`, not `any`. Types re-exported from a `.vue` file, `@nuxt/ui` auto-imports and another module's auto-imports are not modelled and print as `any` on both sides. Values print their type, types their structure, both in the canonical member and union order of the declaration half, so moving an export between scanned files or changing an unexported helper passes. A removed, added or changed line fails, and `--allow-added` never applies to it: move a helper that must stay private under `app/build/`. Repositories without a `dms.frontend.build.ts` print no `Auto-imports:` line.

Both commands end with a table of suppressions in authored code files at the base and at HEAD, for PR bodies to copy: lint directives per rule they name (`*` for a directive naming none), `@ts-expect-error`, `@ts-ignore` and `SAFETY:` comments. The parser finds every comment, after code on the same line too, and skips strings, template literals and JSX text; `.vue` files contribute their script blocks and template comments. Generated output and the agent files `antelopejs-sync` writes are left out as the size guard leaves them out.

Both commands compare **committed HEAD**, not staged or working-tree edits. They check out the base and HEAD in temporary detached worktrees, reuse the current checkout's root and package `node_modules`, and remove the worktrees afterwards. Install the consumer's dependencies before running them.

```bash
pnpm exec antelopejs-api-diff origin/main
pnpm exec antelopejs-comment-proof origin/main
```

## ESLint (Nuxt front ends)

oxlint runs no Vue template rule and no type-aware rule on `.vue` files, so the front end stays on ESLint:

```js
// frontend-vue/eslint.config.mjs
import { antelopeNuxtConfig } from "@antelopejs/tooling-configs/eslint";

export default antelopeNuxtConfig({
  dirs: ["./playground"],
  typeAware: { tsconfigRootDir: import.meta.dirname },
});
```

`typeAware` runs the oxlint preset's type-aware rules, as `@typescript-eslint/<rule>`, on the script blocks of `.vue` files, which `oxlint-tsgolint` cannot read, and with them `antelopejs/no-unsafe-object-assign` and `antelopejs/require-tsconfig-include`. Off when omitted. TypeScript files are left to oxlint, so nothing is type-checked twice. `tsconfigRootDir` is the project root. Each `.vue` file must be listed by its nearest `tsconfig.json`; a file outside it, such as a playground no tsconfig includes, fails to parse. In a Nuxt layer that tsconfig is a `tsconfig.json` that extends the generated `.nuxt/tsconfig.json`, which lists the app and carries the `paths` of the layer's aliases such as `#dms-core/*`, and the lint script runs `nuxt prepare` first so the file exists. That tsconfig sets `compilerOptions.moduleDetection` to `"force"`, as `.nuxt/tsconfig.json` does, so a `<script setup>` that imports nothing is a module; `antelopejs/require-tsconfig-include` reports such a script under any other setting. An import the tsconfig cannot resolve is reported by `antelopejs/require-tsconfig-include`: everything imported through it is an error type, so `no-unsafe-*` would report code that is not unsafe. Types flow from the `.ts` files a component imports. Without Volar, a type imported from another `.vue` file is an error type: `no-unsafe-*` reports code that uses it, which `rules` can switch off, and a `lang="tsx"` block fails to parse. `antelopejs/no-unsafe-object-assign` skips a component with `generic` type parameters, which only Vue's compiler brings into scope.

`antelopeNuxtConfig` also applies `antelopejs/no-comments` and `anti-slop/require-safety-comment-for-type-assertion` to every `.vue` script block and script file, with or without `typeAware`, so a front end follows the same comment rule as the oxlint preset: TSDoc only on a declaration, and a `SAFETY:` comment on every type assertion and non-null assertion.

`antelopeNuxtConfig` inherits the `**/public` ignore of `@nuxt/eslint-config`: no file under a directory named `public` is linted, including a layer source directory with that name. Name such a directory anything else to lint it.

`@nuxt/eslint-config` supplies the Vue and TypeScript rules. The preset only records where AntelopeJS layers differ: single-word page components, `any` and `{}` allowed, `_`-prefixed unused bindings, and import order left alone. It sets no formatting rule, since oxfmt formats `.vue`. Every rule the resolved config sets to warn becomes an error, so no rule warns there either. Pass `rules` to layer your own on top, and declare `@nuxt/eslint-config` in the front end's `package.json`.

## Dependency ranges

An `@antelopejs/*` package ships breaking changes in minor releases, so a range open past the next minor lets an install resolve a breaking release its dependent was never built against. `pnpm run checks` runs `dependency:ranges`, which fails on each `@antelopejs/*` range in `dependencies`, `devDependencies`, `peerDependencies` or `optionalDependencies`, in every `package.json` git tracks, that does not stop below the next minor of its floor, and prints the range to use:

| The floor is… | declare          | also accepted      |
| ------------- | ---------------- | ------------------ |
| 0.x           | `>=0.4.0 <0.5.0` | `^0.4.0`, `~0.4.0` |
| 1.0 or later  | `~1.2.0`         | `>=1.2.0 <1.3.0`   |

A narrower range fails too: `@antelopejs/core` keeps one copy of each interface and refuses to start a module whose range that copy falls outside, so an exact pin (`0.1.7`) breaks startup at the next patch release. `file:` and `link:` specs are skipped. A `workspace:` spec is read as pnpm publishes it, `workspace:^` on a sibling at `1.2.3` as `^1.2.3`, so declare `workspace:~`; it is skipped in a `private` manifest, which is never published. The step runs only in a git checkout whose tracked manifests declare an `@antelopejs/*` package.

In the same checkouts it also runs `dependency:one-range`, which fails when two tracked `package.json` files, the root, workspace packages, playgrounds and e2e folders alike, declare different ranges for one `@antelopejs/*` package in `dependencies`, `devDependencies` or `optionalDependencies`: the lockfile then holds one copy per range. It names each range and the files that declare it. `workspace:`, `file:` and `link:` specs and `peerDependencies` are skipped, since they install no release of their own. It reads the manifests only. A deliberate split is listed in `guardrails.one-range.json` at the root: `{ "exceptions": ["@antelopejs/<name>"] }`.

A range on an `@antelopejs/interface-*` package that is not in the repository must admit the interface version a project loads: `@antelopejs/core` loads one copy of each interface, so a project that installs `interface-dms-automation` 0.7.0 for one module cannot start another whose range stops at `<0.7.0`. When the newest release, the `latest` dist-tag on the registry npm is configured with, of a DMS module names the interface in `antelopeJs.implements`, that release decides: the range must share a release with the range the module declares on the interface. The modules read are `@antelopejs/dms` and those of the [generated DMS module table](./docs/documentation-checks.md#generated-dms-module-table), each published under its repository's name, except one that sits in the repository; a prerelease, or a range semver cannot read, does not count. A project that runs `dms-automation` 0.11.1, which implements `interface-dms-automation` on `>=0.7.0 <0.8.0`, cannot start a module on `>=0.6.0 <0.7.0` or `>=0.8.0 <0.9.0`, so the step fails both and prints the range on the minor that release implements, `use ">=0.7.0 <0.8.0"`. Any other interface must not stop below the package's own `latest`: the step fails `>=0.6.0 <0.7.0` once 0.7.0 is published and prints the range on the minor of that release, `use ">=0.7.0 <0.8.0"`, and a range whose floor is above that release passes. A read of the registry fails after two attempts of three seconds or on an error response. A DMS module the registry answers 404 for has no release. While a DMS module cannot be read, any interface no read release implements is held to the cap alone, since the unread one may implement it, and so is an interface whose `latest` cannot be read, so a registry outage does not fail the step.

When the package sits in the same repository, as in a DMS monorepo, its range must also admit the version there, and `antelopejs-sync` moves it for you: a minor release of a sibling from `0.6.1` to `0.7.0` moves every `>=0.6.0 <0.7.0` on it to `>=0.7.0 <0.8.0`, then sync runs `pnpm install --lockfile-only` so the lockfile follows. The package is not on npm yet when the release hook runs, so the workspace must link it: set `link-workspace-packages=true` in `.npmrc` or `linkWorkspacePackages: true` in `pnpm-workspace.yaml`. When the relock fails, sync leaves the ranges unmoved and exits 1. An interface `.release-it.json` whose `after:bump` hook runs `pnpm --dir ../.. run sync` and `git add -u ../..` commits both with the release. `antelopejs-sync --check` reports the stale range as drift.
